# Mac AI CLI 灵动岛需求设计

- 日期：2026-04-05
- 状态：已完成首版设计，待评审
- 设计对象：运行在 macOS 上的 AI CLI 任务状态中枢
- 设计目标：将 Codex、Claude Code、Gemini CLI 等 AI CLI 的任务执行状态、沟通内容、进度与提醒，统一收敛到一个“灵动岛 + 下拉扩展面板”中，并支持安全的快捷回复

## 1. 背景与目标

当前常见的 AI CLI 工具都各自运行在终端中，任务状态分散、上下文割裂、回复入口分散。用户在并行运行多个 AI CLI 任务时，往往会遇到以下问题：

- 不知道哪个任务正在运行、哪个任务卡住、哪个任务在等自己回复
- 不同 CLI 的进度表达方式不同，难以形成统一的任务感知
- 要频繁切回对应终端窗口才能查看状态或回复消息
- 完成、失败、等待输入等关键事件缺少统一提醒机制

本产品的目标是提供一个 macOS 常驻任务中枢，以灵动岛为入口、下拉扩展面板为主要承载区，实现：

- 统一监控多个 AI CLI 的活跃任务与关键状态
- 在不强制改变现有 CLI 使用习惯的前提下，尽可能被动感知任务进度
- 在可识别且安全的场景中，从灵动岛直接回复对应 CLI 会话
- 用更强的状态化视觉与声音反馈，降低“盯终端”的认知负担

## 2. 产品定位

本产品不是新的终端、不是 IDE、也不是第一版就承担任务调度的编排系统。

第一版定位为：

- AI CLI 的任务监控中心
- AI CLI 的轻量交互入口
- AI CLI 的状态感知与提醒层

不是第一版重点的内容：

- 从灵动岛直接发起复杂新任务
- 跨多个 CLI 自动分发和编排任务
- 替代终端本身的完整工作流

## 3. 设计结论与方案选择

本次设计评估过三条路线：

1. 纯被动监听
2. 被动监听优先 + 桥接适配器
3. 托管启动所有 CLI

最终选择方案 2：`被动监听优先 + 桥接适配器`

选择原因：

- 符合“不强制改变现有 CLI 使用习惯”的产品目标
- 仍为“可靠回复”保留明确的能力边界
- 适合做插件化扩展
- 可以将识别不确定性显式表达为“置信度”，避免过度承诺

该方案的基本原则：

- 监控以被动监听为主
- 回复以显式桥接为主
- 不对所有未知 CLI 承诺稳定双向控制
- 优先保证可解释性与安全性

## 4. 目标用户与典型场景

### 4.1 目标用户

- 同时使用多个 AI CLI 的开发者
- 长时间在终端中与 Agent 协作的高级用户
- 希望在编程、写作、自动化任务执行过程中获得统一任务视图的用户

### 4.2 典型场景

#### 场景 A：多任务后台运行

用户同时在不同终端中运行 Codex、Claude Code、Gemini CLI。灵动岛聚合显示当前最重要的任务状态，例如某个任务正在运行、另一个任务在等待回复。

#### 场景 B：等待用户输入

某个 CLI 任务需要用户补充信息、确认是否继续或回答澄清问题。灵动岛主动提醒，用户不必切回原终端即可在展开面板中回复。

#### 场景 C：任务完成或失败

某个任务执行完成或遇到错误，灵动岛以视觉状态和声音提示通知用户，并展示结果摘要或失败原因片段。

#### 场景 D：查看整体进展

用户想知道当前机器上有多少 AI 任务在运行、多少任务已经完成、多少任务卡住，需要一个总览视图快速判断。

## 5. 产品形态

产品采用两层交互结构：

1. `灵动岛本体`
2. `下拉扩展面板`

### 5.1 灵动岛本体职责

灵动岛本体负责：

- 显示当前最高优先级任务
- 显示来源 CLI、任务状态、短标题
- 显示状态化视觉元素
- 提供少量高频动作入口

灵动岛本体不负责：

- 承载长日志
- 展示多轮完整对话
- 展示复杂多任务列表
- 承载大量低频设置项

### 5.2 下拉扩展面板职责

下拉扩展面板负责：

- 展示任务详情
- 展示时间线与关键事件
- 展示最近对话和日志片段
- 提供快捷回复和自由输入回复
- 展示状态来源和置信度
- 提供诊断信息与恢复建议

## 6. 总体架构

系统由六个核心模块构成：

### 6.1 被动监听层

负责感知系统中的 AI CLI 活跃线索，可能包括：

- 终端窗口信息
- TTY/PTY 会话信息
- 前台应用切换信息
- 可选日志文件监听
- 其他本地事件源

目标是在不改变用户原有 CLI 使用方式的前提下，收集足够多的状态线索。

### 6.2 CLI 适配器层

负责为不同 AI CLI 提供专用解析逻辑与能力声明。

第一版内置适配器：

- Codex
- Claude Code
- Gemini CLI

后续通过插件机制支持：

- OpenClaw
- 其他兼容 CLI

适配器应至少声明：

- 如何识别本工具会话
- 如何识别关键状态
- 是否支持安全回复
- 回复通道如何建立
- 支持哪些快捷动作

### 6.3 会话识别层

负责将零散事件归并成稳定的“任务会话”，核心问题包括：

- 这条输出属于哪个 CLI
- 这条输出属于哪个具体任务
- 当前会话是否仍然活跃
- 该会话是否可回复

会话识别层输出统一的会话对象，供下游使用。

### 6.4 任务聚合与进度引擎

负责将多个会话整理成统一任务流，并推断：

- 当前任务状态
- 所处阶段
- 优先级
- 是否等待用户
- 是否需要提醒
- 是否完成或失败

该层还需要输出置信度和来源依据。

### 6.5 灵动岛交互层

负责将统一任务状态映射为：

- 岛上摘要
- 展开面板内容
- 动态视觉状态
- 声音提示
- 用户交互动作

### 6.6 回复桥接层

负责在满足安全条件时，将用户在面板中的回复投递回正确的 CLI 会话。

回复桥接层必须具备：

- 会话目标确认
- 通道可用性检查
- 发送前校验
- 发送结果反馈
- 失败回退机制

## 7. 核心用户流程

### 7.1 后台观察

用户正常使用 Codex、Claude Code、Gemini CLI。应用在后台持续识别活跃会话，不主动打断。

### 7.2 关键事件上岛

检测到以下关键事件时，灵动岛进入显著状态：

- 新任务开始执行
- 任务长时间运行
- 任务等待输入
- 任务出现异常
- 任务执行完成

### 7.3 岛上摘要感知

用户在岛上看到：

- 来源 CLI
- 当前状态
- 任务短标题
- 状态角色反馈
- 关键动作入口

### 7.4 展开查看并回复

用户点击展开面板后，可以看到：

- 最近关键事件时间线
- 最近若干条对话或日志片段
- 当前阻塞点
- 快捷回复
- 自由输入框

### 7.5 任务收口

任务完成、失败或上下文丢失后，系统展示收口状态与结果摘要，并进入静默态或归入历史列表。

## 8. 任务状态机

第一版推荐状态机如下：

- 已发现会话
- 识别中
- 运行中
- 等待输入
- 可回复
- 异常告警
- 已完成
- 已失败
- 上下文丢失

### 8.1 MVP 必须支持的关键状态

- `运行中`
- `等待输入`
- `可回复`
- `异常告警`
- `已完成`
- `上下文丢失`

### 8.2 状态说明

#### 运行中

任务正在执行，可能没有精确百分比，但系统知道其仍在推进。

#### 等待输入

系统识别到 CLI 正在等待用户的文本输入、确认或补充信息。

#### 可回复

系统能够确认：

- 回复目标会话是谁
- 当前通道可用
- 允许执行回复操作

#### 异常告警

出现报错、重复失败、长时间无推进、识别冲突或其他值得打断用户的事件。

#### 已完成

任务执行结束，系统可展示结果摘要或完成提示。

#### 上下文丢失

系统不再能稳定识别任务归属，例如终端关闭、窗口变化、会话丢失或桥接中断。

## 9. 详细功能需求

## 9.1 会话发现

系统应支持：

- 识别 Codex、Claude Code、Gemini CLI 的活跃会话
- 展示工具来源
- 展示最近活跃时间
- 展示当前是否可回复
- 将不确定归属的会话标记为低置信度

## 9.2 任务状态摘要

系统应支持：

- 将不同 CLI 的输出归一化为统一状态
- 为每个状态附加置信度
- 为每个状态附加来源依据
- 在多任务同时存在时给出优先级排序

## 9.3 会话内容展示

展开面板应支持：

- 展示最近 5-20 条对话或日志片段
- 高亮需要用户关注的消息
- 展示开始、等待输入、恢复、完成、失败等关键事件
- 对错误片段做突出显示

## 9.4 快捷回复

第一版应支持：

- 继续执行
- 重试
- 解释原因
- 停止
- 我补充一点信息
- 自由文本输入

每次发送前都应显示目标会话与目标 CLI。

## 9.5 整体任务看板

系统应提供聚合视图，展示：

- 当前运行中的任务数
- 等待用户的任务数
- 已完成任务数
- 异常任务数

## 9.6 插件化适配器框架

系统应提供插件入口，使新增 CLI 适配器时不需要改动核心 UI 和任务聚合逻辑。

插件接口至少覆盖：

- 会话识别
- 状态识别
- 回复能力声明
- 快捷动作声明
- 事件归一化规则

## 10. 视觉反馈系统

本产品的状态反馈不是纯文本，而是正式的一套状态化视觉语言。

### 10.1 设计方向

第一版采用：`CLI 字符精灵为主，吸收像素游戏感`

这意味着视觉表达应满足：

- 核心气质来自 CLI 字符和终端状态表达
- 角色感来自少量像素游戏式动作和情绪反馈
- 不做重度卡通 IP
- 不做与终端文化完全割裂的 mascot

### 10.2 状态角色定义

灵动岛中存在一个常驻的“字符精灵”，由字符、符号、光标和轻量像素感动效组成，用于传递状态。

### 10.3 核心状态表现

#### 运行中

- 字符循环变形
- 轻微位移
- 持续运算或敲击感

#### 等待输入

- 光标闪烁
- 动作停顿
- 呈现“看向用户”的等待姿态

#### 已完成

- 角色收束为完成态
- 一次短促庆祝动作
- 带轻微通关感

#### 异常/失败

- 字符错位
- 抖动
- 颜色告警
- 感叹符号或阻塞提示

### 10.4 视觉原则

- 优先可识别，不追求复杂动画
- 在灵动岛小空间中也能一眼分辨状态
- 动效应服务状态，不应喧宾夺主

## 11. 声音提示需求

第一版将声音提示纳入正式需求。

### 11.1 声音类型

MVP 支持四类提示音：

- 开始执行
- 等待回复
- 已完成
- 失败/告警

### 11.2 声音风格

- 短促
- 轻量
- 系统级
- 带一点游戏式反馈感
- 不做长时播放

### 11.3 用户控制

用户可设置：

- 全部开启
- 仅关键提示
- 静音

## 12. 信息架构与界面要求

### 12.1 灵动岛本体必须展示

- 当前最高优先级任务
- 来源工具图标或名称
- 状态标签
- 简短任务标题
- 状态角色
- 高优先动作入口

### 12.2 灵动岛本体不应承载

- 长篇日志
- 长段对话
- 多任务复杂列表
- 过多二级操作

### 12.3 展开面板必须展示

- 任务头部信息
- 关键事件时间线
- 最近对话与日志片段
- 回复区
- 诊断区

### 12.4 诊断区内容

诊断区应解释：

- 当前状态为何成立
- 来源于哪些事件或输出
- 当前不确定性是什么
- 为什么允许或不允许回复

## 13. 权限与安全设计

### 13.1 macOS 权限原则

系统可能需要使用：

- 辅助功能权限，用于感知前台窗口、窗口标题、应用状态等

第一版不应默认依赖：

- 屏幕 OCR
- 全屏截图分析
- 任何高侵入性的默认采集方式

### 13.2 回复安全原则

所有回复动作必须满足：

- 可追踪
- 可确认
- 可取消

系统必须清晰展示：

- 将要发送到哪个 CLI
- 将要发送到哪个会话
- 当前是否具备足够置信度

若置信度不足，则：

- 不自动发送
- 仅允许用户手动确认后发送

### 13.3 隐私与数据原则

系统不得：

- 无边界记录所有终端文本
- 默认采集整屏内容
- 在未告知的情况下上传敏感内容到云端做识别

系统应尽量：

- 本地处理状态识别
- 本地存储历史记录
- 对敏感数据做系统级保护或加密保护

## 14. 非功能需求

### 14.1 性能

- 常驻后台时 CPU、内存与电量占用应足够低
- 不应明显影响开发机日常工作

### 14.2 实时性

- 关键状态变化应在秒级反映到灵动岛
- 完成、等待输入、失败等事件提示应及时

### 14.3 可靠性

- 单个适配器故障不应导致全局崩溃
- 识别失败时应优雅降级
- 回复失败时应明确反馈而非沉默失败

### 14.4 可解释性

- 每个重要状态判断都应有来源和置信度
- 用户应能理解系统为何这样判断

### 14.5 可扩展性

- 新增 CLI 适配器时，不应侵入核心 UI
- 核心任务模型应保持稳定

## 15. MVP 范围

### 15.1 MVP 包含

- Codex、Claude Code、Gemini CLI 三个内置适配器
- 被动监听型会话发现
- 统一状态归一化
- 灵动岛摘要展示
- 展开面板详情展示
- 快捷回复与自由回复
- 状态角色基础动效
- 四类提示音
- 整体任务汇总视图
- 插件化适配器框架基础能力

### 15.2 MVP 明确排除

- 从灵动岛直接创建复杂新任务
- 跨 CLI 自动任务编排
- 将产品做成统一终端或 IDE
- 承诺完美准确的百分比进度
- 为每个 CLI 定制完整独立视觉宇宙
- 复杂逐帧动画系统

## 16. 后续版本方向

后续版本可考虑：

- 任务创建与分发
- 多 Agent 协作视图
- 项目级任务总览
- 历史任务检索与复盘
- 自定义快捷回复模板
- 更多 CLI / API Agent 适配器
- 更丰富的角色皮肤与主题

## 17. 关键风险与设计前提

### 17.1 关键风险

- 被动监听天然存在不确定性
- 不同 CLI 的输出风格可能频繁变化
- 回复桥接在不同终端/会话环境中的可靠性不一致
- macOS 权限边界可能影响识别能力

### 17.2 设计前提

- 第一版接受“不是所有会话都能稳定回复”
- 第一版接受“进度更多以阶段表示，而非精确百分比”
- 第一版接受“置信度和来源说明是必要能力，不是附属能力”

## 18. 验收标准

当以下条件满足时，可认为 MVP 需求设计达标：

- 能识别三类内置 CLI 的基础活跃会话
- 能区分运行中、等待输入、完成、异常、上下文丢失等关键状态
- 用户能从灵动岛展开面板中查看最近关键上下文
- 在高置信度场景中，用户能安全回复到原会话
- 状态角色与声音提示能明显区分至少四类核心状态
- 系统能明确告诉用户“当前判断来自哪里、是否可靠”

## 19. 推荐下一步

本需求设计确认后，下一步应进入实现规划阶段，建议拆为以下子项目：

1. 核心任务模型与状态机
2. macOS 灵动岛与展开面板原型
3. CLI 适配器与事件归一化框架
4. 回复桥接与安全校验机制
5. 状态角色与声音反馈系统
