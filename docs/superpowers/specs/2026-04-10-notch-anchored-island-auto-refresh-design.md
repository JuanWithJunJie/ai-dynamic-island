# MacIrland 刘海挂靠 Island、自动刷新与紧凑 Panel 需求文档

## 文档信息
- 日期：2026-04-10
- 状态：草案
- 参考素材：`example/macirland-1.mp4`
- 目标版本：island-first 顶部体验收口

## 1. 背景

当前 MacIrland 已经完成了 island-first 的主体形态：
- 顶部 compact island
- highlighted single-task card
- attention queue / interruption handoff
- panel 作为二级详情层
- 真实 reply bridge 的产品层收口

但从体验上看，还有两个明显问题：

1. **顶部 island 仍然“悬”在菜单栏下方**
   当前实现使用 [IslandCoordinator.swift](/Users/lijunjie/Documents/AIproject/macirland/MacIrlandApp/App/IslandCoordinator.swift) 中基于 `visibleFrame` 的定位方式，把 island 放在菜单栏可视区域之下，并额外留了 `6pt` 顶部间距。这样更像“顶部浮窗”，而不是“贴着刘海的系统层”。

2. **panel 仍保留手动刷新按钮**
   当前 panel header 里还有手动刷新按钮，见 [PanelView.swift](/Users/lijunjie/Documents/AIproject/macirland/MacIrlandKit/Features/Panel/PanelView.swift)。这会让产品显得偏工具化，也与“持续在线的顶部状态层”定位不一致。

3. **panel 体量仍明显大于参考产品**
   当前 panel 仍然接近“深色工作台”，窗口底盘和内容铺陈都偏大。即使 island 已经成为第一层，二级 panel 仍然显得过重，和参考产品相比缺少那种“轻量 detail sheet”的感觉。

参考录屏 `example/macirland-1.mp4` 想表达的产品感更明确：
- 产品应该像一个直接挂靠在刘海顶部的状态岛
- 产品不要求用户手动点刷新
- 它应该持续自行更新，让用户只负责“看”和“介入”

因此，下一步需要把 MacIrland 再往“系统顶部状态层”推进一刀：
- island 贴近刘海顶部挂靠
- 删掉手动刷新按钮
- 改成固定 1 秒自动刷新
- 把二级 panel 收成更接近竞品体量的紧凑详情层

## 2. 核心结论

### 2.1 可行性结论
这两个改动都可以做。

### 2.2 系统边界
需要明确一个 macOS 边界：
- **不能真的把 UI 画进物理刘海黑区内部**
- 也不能替代系统菜单栏本身

本次目标不是“占用刘海区域本体”，而是：
- 让 island 在视觉上**紧贴刘海底边 / 顶部系统条**
- 形成“挂在刘海位置”的感受
- 尽量减少它像普通浮窗的感觉

因此，本次设计目标应表述为：
> **notch-anchored top island**
>
> 一个贴近刘海顶部、视觉上与刘海区域耦合的顶层 island，而不是一个悬在菜单栏下方的自由浮窗。

## 3. 核心目标

### 3.1 主目标
让 MacIrland 的 island 视觉上直接挂靠在刘海顶部，并且以固定 1 秒自动刷新替代 panel 手动刷新。

### 3.2 具体目标
1. island 的默认位置应比当前明显更靠上，视觉上贴近刘海区域。
2. compact 与 highlighted 两种形态都要采用同一套顶边挂靠策略。
3. panel header 中不再出现手动刷新按钮。
4. 应用启动后自动进入固定 `1s` 轮询刷新。
5. 用户不需要再通过“点刷新”来拉取最新任务状态。
6. panel 视觉体量明显收小，更像 island 下方的二级 detail sheet，而不是独立的大工作台。

## 4. 非目标
本轮不做以下内容：
- 不修改 island 的主视觉语言
- 不新增 hover、拖拽、手势
- 不重写 observation / adapter / reply bridge
- 不新增“手动开关自动刷新”的设置项
- 不把刷新频率改成自适应策略
- 不引入新的 panel 交互模式或分页导航

## 5. 当前问题分析

### 5.1 顶部定位问题
当前 `IslandCoordinator.layoutWindow()` 使用：
- `screen.visibleFrame`
- `visibleFrame.maxY - size.height - 6`

这会带来两个结果：
- island 一定在菜单栏可视区域之下
- 它和顶部之间始终存在明显间隙

所以它看起来像：
- 顶部悬浮提示框

而不是：
- 系统顶部挂靠状态岛

### 5.2 刷新交互问题
当前 panel header 右侧有刷新按钮：
- 用户要理解“状态可能不是实时的”
- 用户要学会“点按钮才能拉新”

这更像后台管理工具，而不是实时状态产品。

对于 island-first 产品来说，更自然的心智应当是：
- 产品默认持续刷新
- 用户只在需要时介入
- 刷新不应该成为显式动作

### 5.3 Panel 体量问题
当前 panel 之所以显得“大”，不只是窗口尺寸大，还包括：
- 窗口底盘本身偏大
- 首屏同时摊开多个 section
- 卡片 padding、间距和留白都偏宽

这意味着本轮不能只“把窗口缩小”，否则只会让现有内容变拥挤。  
正确做法应当是：
- **缩小窗口**
- **同步压缩首屏内容密度**
- **把 panel 明确收成二级 detail sheet**

## 6. 方案评估

### 方案 A：只删除刷新按钮，不改定位
优点：
- 风险低
- 开发快

缺点：
- 不解决“看起来还是浮在菜单栏下方”的问题
- 与参考视频的感受差距仍大

### 方案 B：改成刘海挂靠 + 固定 1 秒自动刷新
优点：
- 最接近目标体验
- 能直接提升“这是顶部系统层”的感觉
- 删掉刷新按钮后产品会明显更轻
- 适合顺手把 panel 收成更像竞品的紧凑二级层

缺点：
- 需要更谨慎处理顶边坐标
- 固定 `1s` 轮询会增加 observation/AppleScript 压力
- panel 不能只改尺寸，必须同步收内容

### 推荐方案
采用方案 B。

用户已经明确选择：
- 贴近刘海顶部挂靠
- 删除手动刷新按钮
- 固定 `1s` 自动刷新
- 把 panel 做得更小、更接近竞品体量

## 7. 设计方案

## 7.1 顶部挂靠策略

### 目标状态
island 不再根据 `visibleFrame` 定位，而改成基于 `screen.frame` 的顶边挂靠。

compact / highlighted 都采用同一条原则：
- 水平仍保持居中
- 垂直位置尽可能靠近屏幕顶边
- 保留很小的安全边距，避免和菜单栏/窗口阴影产生脏边

### 建议定位原则
1. 使用 `screen.frame` 作为顶边参考，而不是 `visibleFrame`
2. 引入统一常量，例如：
   - `topAnchorInset`
3. compact 和 highlighted 使用同一 `y` 起点逻辑
4. 顶部 inset 应明显小于当前 `6pt + visibleFrame` 方案

### 预期体验
从视觉上看：
- island 会像挂在刘海下沿
- 而不是悬在菜单栏下面

### 明确不做
- 不尝试把窗口真实绘制到刘海黑区内部
- 不抢占系统菜单栏空间
- 不对不同机型手写刘海尺寸数据库

## 7.2 自动刷新策略

### 目标状态
应用启动后自动开始固定 `1s` 刷新，不再要求用户手动点刷新。

### 刷新机制
建议在 App 层或 store 周边引入统一 refresh scheduler：
- 启动时开始
- app 存活期间持续调度
- 每 `1.0s` 触发一次 `viewModel.refresh()` / `store.refresh()`

### 生命周期要求
1. app 启动时启动 scheduler
2. app 退出时停止 scheduler
3. island / panel 打开关闭不影响 scheduler 存在

### 刷新职责
自动刷新属于应用级行为，而不是某个 view 的局部行为。

因此不建议：
- 把 timer 放到 `PanelView`
- 把 timer 仅绑定到 panel 是否显示

更合理的是：
- 由 `AppDelegate` 或独立 coordinator/refresh controller 持有

## 7.3 刷新按钮处理

### 目标状态
panel header 中删除刷新按钮。

### 结果
header 只保留：
- 品牌标题
- 一句当前状态副标题

不再保留：
- `arrow.clockwise`
- 明示“手动拉取”的产品心智

## 7.4 空态和错误态文案更新

当前部分空态文案仍写着：
- “点击右上角刷新重试”

本轮必须同步改掉这类文案。

更新方向：
- 改成“等待系统下一轮刷新”
- 或“请确认权限后稍等片刻”
- 或“如果状态未恢复，请重新启动终端会话”

总之，不能再出现依赖手动刷新按钮的表述。

## 7.5 紧凑 Panel 策略

### 目标状态
panel 不再像一个独立的大工作台，而是更接近：
- island 下方的二级 sheet
- 一个可继续介入的紧凑详情层

### 目标尺寸
建议把当前大致 `760 x 820` 的体量收敛到：
- 宽度目标：`640`
- 高度目标：`560` 左右

允许在实现时做小幅浮动，但方向必须明确：
- 明显比当前更窄
- 明显比当前更矮

### 首屏内容策略
要实现更小体量，必须同步做内容压缩：

#### 保留
- 标题区
- 当前任务摘要
- 1 行或 2 行关键动作
- 最近 1-2 条关键 timeline

#### 收起或降级
- `任务列表`：默认折叠或只保留极轻摘要
- `自由输入`：默认折叠或缩成次级入口
- `诊断`：继续保持折叠
- `最近关键阶段`：只显示最近 1-2 条
- `快捷回复`：优先只保留最关键的少量动作

### 设计原则
1. 不能只是把大 panel 硬塞进小窗口
2. panel 仍要可用，但不再承担首层信息爆炸
3. 从视觉上看，它应该是 island 的延伸，而不是另一个主界面

## 8. 架构影响

### 8.1 需要新增的概念
建议新增一个应用级自动刷新协调层，例如：
- `RefreshCoordinator`
- 或等价命名

职责：
- 管理定时器
- 固定节流到 `1s`
- 调用 `TaskStateStore.refresh()`

### 8.2 不建议的做法
不建议直接在多个 view 里各自 `Timer.publish(...)`，因为：
- 生命周期难控
- 可能重复刷新
- 会让 panel / island 与刷新机制耦合过深

### 8.3 现有依赖影响
固定 1 秒刷新会直接增加：
- Terminal AppleScript 读取频率
- iTerm AppleScript 读取频率
- observation snapshot 生成频率

因此本轮必须把它当成“产品决定”，而不是默认零成本变化。

### 8.4 Panel 协调层影响
panel 尺寸压缩意味着：
- `PanelCoordinator` 的窗口尺寸常量需要调整
- `PanelView` 的 section 组织需要进一步压缩
- `SessionDetailView` 首屏元素需要更强的优先级排序

但这仍应被视为“现有二级层的收口”，而不是重新发明一套 panel 架构。

## 9. 风险与权衡

### 9.1 性能风险
固定 `1s` 刷新会提高 CPU 与 Apple Events 调用频率。

### 9.2 权限噪音风险
如果权限没开，1 秒轮询会更快暴露错误态。
这不是坏事，但要确保 UI 错误提示足够稳定，不要闪烁。

### 9.3 顶部定位风险
不同屏幕、外接显示器、是否刘海屏，顶边表现会不同。
所以实现时应保证：
- 在刘海屏上“贴顶”
- 在非刘海屏上也不显得突兀

### 9.4 Panel 可用性风险
如果 panel 收得过小，但内容未同步减重，体验会恶化。

因此必须遵守：
- 先明确“哪些是首屏必要信息”
- 再缩窗口
- 不接受“只是把现在 panel 缩小”的实现

## 10. 成功标准

本轮完成后，应满足：

1. island 位置比现在明显更靠近顶部，视觉上挂在刘海区域。
2. panel header 不再出现刷新按钮。
3. 应用会固定每 `1s` 自动刷新一次。
4. 空态/错误态文案里不再提“点击刷新”。
5. app 启动后无需用户操作，也会持续更新任务状态。
6. panel 明显比现在更小，且仍可完成主要介入流程。
7. `swift test` 和 `swift build` 保持通过。

## 11. 验证方式

### 11.1 代码验证
- unit tests 覆盖：
  - island 顶部挂靠定位逻辑
  - 自动刷新 scheduler 存在与周期配置
  - panel header 不再包含刷新按钮
  - 空态文案不再依赖手动刷新
  - panel 使用新的紧凑尺寸常量
  - panel 首屏不再同时展开过多 section

### 11.2 实机验证
- 启动 app
- 观察 island 是否贴顶
- 打开 panel
- 确认没有刷新按钮
- 确认 panel 体量明显缩小
- 确认主要流程仍然可用
- 等待数秒，确认会话状态会自动变化/拉新

## 12. 实施建议

建议拆成一个独立 implementation plan，再执行代码修改。  
优先顺序建议：

1. 顶部挂靠定位
2. 应用级自动刷新协调器
3. 删除 panel 刷新按钮
4. 收小 panel 窗口和首屏内容密度
5. 文案收口
6. 测试与实机验证

## 13. 结论

这一步不是“再修一个小 UI”，而是把 MacIrland 从：
- 顶部浮窗 + 半手动工具

推进到：
- 挂靠刘海顶部的持续在线状态岛

其中最关键的产品变化不是 island 往上挪了多少像素，而是：
- 用户不再负责刷新
- 产品开始自己持续更新
- 顶部状态层的系统感显著增强
- panel 不再像一块单独的大工作台，而是更像 island 的二级延伸

这会是从“现在已经能用”走向“更像一个完整产品”的重要一刀。
