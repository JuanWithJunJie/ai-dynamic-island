# MacIrland Island-First 形态需求文档

## 文档信息
- 日期：2026-04-09
- 状态：Phase 5 实施计划已完成
- 目标版本：下一阶段产品形态收敛
- 参考素材：`example/vibe-irland.mp4`、`example/vibe-irland-1.mp4`
- 设计方向：从 `panel-first` 过渡到 `island-first`

## 1. 背景
当前 MacIrland 已经具备较强的 panel 能力：
- 会话发现与优先级排序
- 主会话详情
- quick actions
- 自由输入回复
- runtime history 预览
- diagnostics 排障区

这套能力适合“打开后介入处理”，但还不够接近参考录屏里的产品感受。

参考录屏呈现的不是一个完整工作面板，而是一个贴近刘海顶部区域的轻量悬浮工作岛：
- 默认只显示极少信息
- 有关键事件时才扩展
- 扩展后也只突出一条最重要的任务
- 用户可以在 1-2 秒内理解“现在发生了什么”

因此，当前问题已经不再只是“panel 里删掉哪些内容”，而是产品主形态需要转向：
- 让 `island` 成为第一入口和第一信息层
- 让 `panel` 退到二级详情层
- 把“看一眼就知道需不需要处理”作为默认体验

## 2. 核心目标

### 2.1 主目标
把 MacIrland 从“以展开面板为中心的任务控制台”收敛成“以顶部悬浮 island 为中心的任务提醒与介入入口”。

### 2.2 具体目标
1. 默认状态下，用户无需主动打开 panel，也能感知当前是否有需要关注的会话。
2. 当有高优先级会话出现时，顶部 island 应能用单条卡片清晰表达：
   - 是谁
   - 现在什么状态
   - 是否需要我介入
3. 首层展开形态应尽量只突出一条最重要的会话，而不是同时展示多个模块。
4. panel 保留，但退为“需要进一步处理时再进入”的二级空间。
5. 整体视觉应更贴近动态岛/顶部 toast，而不是传统悬浮工具面板。

## 3. 非目标
本轮不做以下内容：
- 不重写 observation / adapter / session matching 核心逻辑
- 不新增复杂的多任务编排能力
- 不在第一版 island 里承载完整 diagnostics
- 不让 island 直接承担全部自由输入与长历史浏览
- 不追求一开始就复刻参考录屏的所有动画细节

## 4. 参考录屏结论
基于 `example/vibe-irland.mp4` 与 `example/vibe-irland-1.mp4`，参考产品有几个关键特征：

### 4.1 常态不是纯入口，而是持续可读状态条
顶部常态是一条贴近刘海区域的黑色长胶囊，除了品牌图标外，还会稳定显示：
- 当前状态词，例如 `运行中`、`工作中...`
- 会话计数，例如 `1 个会话`

这说明 compact 态不是“只负责打开面板”的入口，而是首层状态摘要本身。

### 4.2 事件驱动展开
当出现高优先级事件时，胶囊会扩展成一张横向卡片，展示单条内容，而不是展开完整工作台。

### 4.3 单任务优先
扩展态里几乎所有视觉注意力都服务于一条任务：
- 左侧来源/品牌
- 中间标题 + 摘要
- 右侧来源标签 + 时间

### 4.4 展开态保留大量留白
展开后的大卡片并不会把内容铺满，而是只把关键信息压在左下或左侧一小块区域，其他区域大量留白。

这说明它不是想把“更多信息塞进去”，而是在强调：
- 这是一个顶部提示层
- 不是一张完整工作面板

### 4.5 全局控制与内容分层明显
展开态右上角会长期保留少量全局控制图标，例如声音或设置。

这些控件属于产品壳层，不属于当前任务内容本身。也就是说，它把：
- 产品级 controls
- 当前会话内容

明确拆成了两层。

### 4.6 极轻视觉噪音
整体风格依赖：
- 黑色整体背景
- 少量高亮标签
- 少量图标
- 极弱边框和极少分区

### 4.7 动效是核心体验的一部分
“从窄胶囊 -> 展开提示卡 -> 收回胶囊”的连续形变，是产品辨识度的重要来源。

## 5. 我们与参考效果的关键差异

### 5.1 当前形态差异
当前 MacIrland 更像：
- 常驻状态栏入口
- 点击后打开 panel
- panel 内完成识别、判断、处理

参考产品更像：
- 顶部 island 本身就是主要体验
- panel 甚至可以不存在，或只是次级详情

### 5.2 信息层级差异
当前首层仍偏“控制台”：
- header
- session 列表
- 主会话区
- quick replies
- history
- diagnostics

参考产品首层则偏“单卡片提醒”：
- 只给当前最重要的信息
- 其他内容一律不抢注意力

### 5.3 视觉重心差异
当前视觉重心在“面板内容组织”。
参考产品视觉重心在“顶部形态本身”和“展开动画”。

### 5.4 交互路径差异
当前路径：
`看到入口 -> 打开 panel -> 看主会话 -> 再决定是否处理`

目标路径：
`看到 island -> 立即理解状态 -> 必要时一键进入更深层处理`

## 6. 设计结论与方案选择
本次评估三条路线：

### 方案 A：继续优化 panel，island 只做入口
做法：
- 维持现有架构
- 继续精简 panel
- 顶部入口仍只是菜单栏按钮

优点：
- 改动小
- 基于现有成果推进快

缺点：
- 很难获得参考录屏那种“产品第一印象”
- 岛本身仍然不是主体验

### 方案 B：新增轻量 island 层，panel 作为二级详情
做法：
- 增加真正的顶部悬浮 island
- island 默认极简，事件驱动扩展
- panel 只在点击/展开后出现

优点：
- 最接近参考录屏
- 能同时保留我们已经做好的 panel 能力
- 适合渐进式演进

缺点：
- 需要重新梳理两层产品边界
- 对动画和状态切换要求更高

### 方案 C：完全转成 island-only
做法：
- 取消 panel 作为主承载
- 所有核心操作尽量压进 island

优点：
- 最极致

缺点：
- 风险过高
- 会压缩当前 reply / history / diagnostics 的可用空间
- 不适合当前产品阶段

### 推荐方案
采用方案 B：`新增轻量 island 层，panel 退为二级详情`。

原因：
- 既能获得接近参考录屏的产品气质
- 又不会浪费我们已经完成的 panel、history、reply 能力
- 能用较低风险分阶段落地

## 7. 目标产品形态
产品改成两层结构：

1. `顶部 island`
2. `二级 panel`

其中：
- island 是默认体验
- panel 是深度处理体验

### 7.1 顶部 island 的职责
负责：
- 显示当前最重要的会话
- 表达是否需要用户介入
- 承担最轻量的提醒和跳转
- 给出极少数高频动作

不负责：
- 展示完整多会话列表
- 展示长时间线
- 展示完整 diagnostics
- 承担长文本输入

### 7.2 二级 panel 的职责
负责：
- 承接更深的介入处理
- 展示 runtime history 预览/完整历史
- 承接自由输入回复
- 浏览其他 session
- 查看 diagnostics

## 8. Island 信息架构

### 8.1 常态：Compact Island / Status Strip
默认显示：
- 品牌图标
- 一个当前状态词
- 一个会话计数

原则：
- 比传统图标入口更宽，但仍保持单行
- 尽量稳
- 永远可一眼识别
- 让用户不打开任何面板，也知道系统当前是否在工作

当没有活跃任务时：
- 仍保留图标
- 状态文案可回落到 `空闲` / `就绪`
- 数字可为 `0`

当有活跃任务时：
- 状态词优先表达系统当前总体状态，例如 `运行中`、`等待处理`
- 会话计数表达总量，例如 `1 个会话`

不建议 compact 态显示：
- 长标题
- 多个 tag
- 长摘要
- 原始诊断信息

### 8.2 扩展态：Single-Task Island Card
当出现高优先级事件时，扩展为单条任务卡。

保留内容：
- 产品级全局 controls，例如声音、设置
- 左侧品牌/来源图标
- 主标题：`会话标题` 或 `来源 + 当前意图`
- 副标题：一句摘要或一句用户该做什么
- 右侧来源标签，例如 `Codex` / `Claude Code`
- 时间标签，例如 `<1m`

可选弱信息：
- 一条更低权重的次级说明
- 1 个主动作按钮

布局原则：
- 内容区只占卡片的一小部分
- 保留大面积留白
- 不把大卡片做成多模块容器

不应出现的内容：
- 多张卡片并列
- 多行 chips 堆叠
- 完整 session 列表
- diagnostics 原始文本

### 8.3 Expanded Card 内部分层
展开卡建议拆成两层：

1. `chrome layer`
   - 全局声音开关
   - 设置入口
   - 可选关闭/忽略入口

2. `content layer`
   - 当前主会话图标
   - 标题
   - 摘要
   - 来源标签
   - 时间
   - 可选的一条弱信息

这样可以避免把产品壳层按钮和任务正文混在一起。

### 8.4 高优先级状态表达
以下状态允许触发 island 扩展：
- waiting input
- reply available
- failed
- alert
- completed（可选，低优先级）

状态优先级建议：
1. `waitingInput`
2. `replyAvailable`
3. `failed`
4. `alert`
5. `running`
6. `completed`

默认只扩展展示最高优先级的一条。

### 8.5 状态机建议
建议 island 至少有四个视觉状态：

1. `idle`
   - 空闲/就绪
   - 显示图标 + `空闲` + `0`

2. `summary`
   - 有活跃会话，但没有强提醒
   - 显示图标 + 状态词 + 会话数

3. `highlighted`
   - 出现需要被感知的高优先级事件
   - 从 summary 扩展成 single-task card

4. `engaged`
   - 用户点击后，进入 panel 或更深层操作

状态转换建议：
- `idle -> summary`：检测到活跃会话
- `summary -> highlighted`：出现 waiting / failed / alert 等高优先级事件
- `highlighted -> summary`：超时收回或用户关闭
- `highlighted -> engaged`：用户点击卡片主体
- `engaged -> summary`：panel 关闭或焦点回收后返回常态摘要

## 9. 交互设计

### 9.1 基础交互
- 单击 compact island：展开 single-task island card
- 单击 expanded card 主体：打开 panel 并定位到当前主会话
- 点击关闭/忽略：收回到 compact 状态

### 9.2 自动收回
建议扩展卡支持自动收回：
- `running` 类信息短暂停留后自动收回
- `waitingInput` / `failed` 不自动立即消失，可等待用户明确处理或延时更长
- 自动收回后不应回到“无感入口”，而应回到仍可读的 compact 状态摘要

### 9.3 快捷动作边界
island 层只允许极少量动作：
- 打开 panel
- 可选的 1 个推荐 quick action

不建议第一版就在 island 里承载：
- 多个 quick actions
- 自由输入框
- 长文本编辑

### 9.4 多任务策略
同一时刻只突出一条任务。

如果有多个高优先级任务：
- compact 态只显示总数
- expanded 态显示优先级最高的一条
- 其余任务留给 panel 浏览

### 9.5 状态词策略
compact 态里的状态词不应直接照搬底层枚举，而应做面向用户的归一化表达。

建议优先只保留少量状态词：
- `空闲`
- `运行中`
- `等待处理`
- `需关注`
- `已完成`

避免在首层暴露太工程化的状态词，如：
- `replyAvailable`
- `contextLost`
- `recognizing`

## 10. 与当前 panel 的关系

### 10.1 panel 需要保留
当前 panel 已经具备较成熟的介入处理能力，不应删除。

### 10.2 panel 需要进一步角色收敛
panel 应从“默认第一入口”调整为：
- island 的详情承接层
- 更深一步的处理空间

### 10.3 首层与二层的边界
island 负责回答：
- 现在谁最重要？
- 要不要我管？

panel 负责回答：
- 具体怎么处理？
- 其他会话怎么样？
- 为什么识别失败？

## 11. 视觉方向

### 11.1 风格关键词
- notch-adjacent
- black glass
- single focus
- low noise
- high contrast
- soft motion

### 11.2 视觉原则
- 一个主容器，不做多卡片堆叠
- 信息只分主副两级
- 标签和时间是辅助，不抢主标题
- 默认常态的视觉存在感要低，但可识别性要高
- expanded 态的大面积留白应被视为设计资产，不是待填充空间
- controls 放在壳层，内容放在内容层，避免混排

### 11.3 动效原则
- 默认从 compact 到 expanded 使用连续形变
- 尽量避免硬切
- 动画服务于“状态变化被感知”，不是为了炫技

## 12. 技术与平台约束

### 12.1 菜单栏约束
macOS 状态栏位置由系统决定，第三方 app 不能精确控制坐标。

因此，若要接近参考录屏的“顶部中间稳定形态”，不能只依赖传统 `NSStatusItem` 菜单栏入口。

### 12.2 形态实现约束
这意味着 island-first 方案大概率需要：
- 独立悬浮窗口或 overlay 窗口
- 更像 HUD / top anchored surface 的实现
- 与传统菜单栏入口并存或替代

### 12.3 演进策略
第一版可以保留当前状态栏入口和 Dock 入口，作为保底导航。
真正的 island 形态可以作为新增层逐步接管首屏体验。

## 13. 分阶段落地建议

### Phase 1：增加顶层 compact island
目标：
- 在现有 panel 之外新增一个顶部悬浮 compact status strip
- 显示图标 + 状态词 + 会话数
- 点击后打开 panel

价值：
- 先把“默认入口形态”从菜单栏项切出来
- 先建立持续可读的第一信息层

### Phase 2：增加 expanded single-task card
目标：
- 支持在高优先级事件时，从 compact island 扩展成单条任务卡
- 展示标题、摘要、来源、时间
- 引入壳层 controls 与内容层分离
- 点击后进入 panel

价值：
- 初步获得参考录屏里的产品感觉

### Phase 3：加入最小快捷动作
目标：
- 在 expanded 态只加入 1 个推荐动作
- 保持极轻交互，不把它做成完整 panel

价值：
- 提高“看到提醒 -> 立刻处理”的闭环效率

### Phase 4：细化动效与策略
目标：
- 细化不同状态的展示时长、收回策略、动画节奏
- 调整优先级切换和打断规则

价值：
- 让体验真正稳定、耐用，而不只是“长得像”

## 14. 成功标准
如果这次方向正确，用户应能明显感受到：

1. 不打开 panel，也能知道当前是否有重要任务。
2. 第一眼看到的是“最值得关注的一条”，不是一个复杂控制台。
3. 整体产品气质更接近动态岛式提醒器，而不是开发工具面板。
4. panel 的存在感降低，但处理能力没有丢。

## 15. 下一步建议
这份文档确定的不是一个纯视觉改造，而是主入口形态调整。

建议下一步不要直接改现有 panel 细节，而是先单独写一份实现计划，聚焦：
- 是否引入独立顶部悬浮窗口
- compact island 与 expanded card 的状态机
- 与当前 panel、status bar、Dock 的并存关系
- 哪些现有 view/model 可以复用，哪些需要新增
